# Agent Office Floor (in progress)

A local, read only browser view of selected OpenClaw sessions. The implementation follows [`docs/office_specifications_v0.9.md`](../docs/office_specifications_v0.9.md). It is not yet a verified release of the specification.

## Reproducible baseline

- Munder Difflin source: `9e26ca5f692ba00d50334c79f4b6d36416e3bffa`. Selected source hashes are in [`packages/office-scene/UPSTREAM.md`](packages/office-scene/UPSTREAM.md).
- Target OpenClaw API version for this implementation: `2026.9.4`. Check the installed CLI and Gateway versions, granted scope, and device pairing on each deployment.
- Gateway client and protocol packages: `2026.9.4` each. Browser and build dependencies are exactly pinned in `package-lock.json`.
- Restricted upstream tilesets and maps are excluded. The default map and atlas are original project assets. The MD procedural character pipeline is vendored with eight additional project-owned specialist recipes.

## Local development

```sh
cd agent-office-floor
npm ci
npm test
npm run typecheck
npm run build
npm run start -w @pap/office-server
```

The app listens on `127.0.0.1:${PORT:-4174}`. It serves `GET /api/floor/state`, `GET /api/floor/events`, `GET /api/floor/coverage`, `GET /api/floor/progress?id=…` for the selected visible session, `GET /api/pap/tasks`, and `GET /healthz`. The coverage endpoint contains only aggregate message-subscription counts and read-queue length, without session keys or names. The progress endpoint returns no card payload; an authorized card read updates the state stream. The PAP endpoint runs a read-only local projector that emits agent, schedule and run metadata from the PAP manifests, ignored config and run ledger; it omits task inputs, responses and errors. New PAP starts record a Linux process ID plus process start identity. The projector checks both before reporting a still-existing process, without sending either value to the browser. A start without a terminal record and without a matching process is shown as unconfirmed. A surviving process does not by itself prove its task is still executing. Forecast dispatch times include scheduler jitter when its seed exists, and actual execution depends on a running `pap tick` service. Only loopback requests with a loopback Host are accepted in local mode. The portal mode requires a separate application observer login; actual portal routing is not yet accepted. No Gateway credentials reach the browser.

The browser sends an ephemeral same-origin visibility hint to `POST /api/floor/view`; it contains only a random page ID and a visible flag. When no page is visible, Gateway fallback polling uses a 15-second interval. Returning to a visible page requests an immediate calibration. Hints expire after 45 seconds if a tab disappears without reporting its departure.

The authenticated FloorState response retains the original session key and session-instance ID required by specification 0.9. Those addresses can contain channel recipient metadata, so the local service remains loopback-only and portal mode requires its separate observer password. The visible scene and roster use opaque short cues instead of printing raw addresses. Composite run IDs, tool call IDs and event references are replaced with stable process-local identifiers in browser responses; the server retains their originals for event correlation.

## Portal preparation

The repository declares the app in `.openclaw/portals.json` for an OpenClaw agent with the `portal` tool. It uses dedicated port 4184; the local-only office on 4174 must never be exposed through a portal. The declared command forces portal mode and honors the `PORT` returned by the portal tool. The clean-source archive includes this declaration and excludes other `.openclaw/` files. The declaration does not start the server or inject secrets. The OpenClaw `portal` capability is an agent tool, not an `openclaw portal` CLI command. The pinned OpenClaw documentation says SSH-backed Codex sessions do not have this tool. Opening a portal requires a separately authorized write scope; actual Control UI delivery needs verification on the target installation.

Ask a Gateway-hosted OpenClaw coding agent to open the declared port first, then start the declared command as a background process with the returned `PORT` and token-free `PUBLIC_URL` in its ignored launch environment. Supply a private `PAP_OFFICE_VIEWER_SECRET` of at least 24 characters and the exact Gateway observation credential through that environment. The server refuses to start in portal mode without `PUBLIC_URL` or the viewer secret. Optional `PAP_OFFICE_EMBED_ORIGIN` must be the exact Control UI origin when iframe display is intended; HTTPS and loopback HTTP are accepted, while non-loopback HTTP is rejected. Without it, the CSP allows a separate tab but blocks cross-origin embedding. The app rejects non-HTTPS portal URLs except loopback HTTP. It still listens only on loopback.

In portal mode, the app shows a plain password form before serving any state, identities, task metadata, progress reads, assets or SSE. A successful unlock creates one in-memory, HttpOnly observer cookie; restarting the server invalidates it. This is an application access check because OpenClaw portal launch URLs are transferable bearer links and the proxy does not pass an authenticated viewer identity to the app. The test suite verifies the local HTTP boundary, including a simulated forwarded request. Actual portal routing, cookie rewriting, browser embedding and SSE forwarding must still be checked through the returned portal URL before enabling remote access. Do not put the observer secret or portal bearer URL in tracked files, logs or screenshots.

The login form uses `Referrer-Policy: same-origin` for direct local access; all other office responses use `no-referrer`. The pinned OpenClaw portal proxy overrides that policy with `no-referrer`, which can make Chrome submit the form with `Origin: null`. Portal mode accepts that form submission only when the proxy's forwarded host and scheme match the configured token-free `PUBLIC_URL` and a forwarded client address exists; the observer password is still required. Foreign origins and unforwarded null origins are denied, and CSP restricts form submission to the same origin. An isolated local portal-mode browser login, real read-only Gateway view, SSE stream and cookie invalidation after restart have passed. A separate local proxy reproducing the pinned Host rewrite and policy completed a Chrome login with `Origin: null`. These checks do not replace testing an actual OpenClaw `portal.open` and Control UI embed.

When an authenticated page receives HTTP 401 or 403 from an office API, it immediately removes the rendered office DOM and navigates back to the observer login page. The first SSE failure also checks the state endpoint so a restarted server's invalidated cookie is detected promptly. A strict-CSP browser fixture can replay this with `PORT=5198 PAP_CSP_AUTH_EXPIRE_DELAY_MS=3000 node --import tsx tests/browser/csp-server.ts` and `/index.html`; it serves a synthetic office, ends SSE, returns 401 on the next state read, and then serves the login page at `/`.

To replay a Gateway read-permission revocation through the production browser bundle, run the strict-CSP fixture with `PAP_CSP_REVOKE_DELAY_MS=12000`. Select one synthetic session before the timer expires. The fixture sends a valid SSE patch removing all 12 synthetic rows and their handoffs, marks session-list access forbidden, and serves the revoked snapshot on later HTTP reads. The browser should show “需要授权”, zero roster rows and an empty detail panel. This tests the browser projection and scene inputs; it does not revoke permissions on the real Gateway.

The SSE endpoint sends each new viewer a snapshot immediately. It merges consecutive ordinary state patches over 100 ms while preserving revision order. Terminal, waiting, failure, stale, degraded, offline and explicit removal changes are sent immediately; a queued update for a removed row is collapsed into the removal patch.

`GET /api/floor/identities` emits only selected agent IDs, display names and a Feishu-app flag. The identity panel includes selected agents without sessions and puts Feishu-bound agents first. The separate OpenClaw activity list links fresh running, waiting and queued sessions directly to their scene pages, even when a current row lacks a recent-activity timestamp. A second list links the eight most recently updated fresh terminal rows, labeled with their record-update time; the timestamp orders results but does not determine their outcome. Scene pages show one recent session per identity before repeating that identity, while every session remains an independent figure. The searchable session roster displays 50 rows per page to keep large histories manageable. Visible roster and scene labels use stable opaque FloorId suffixes instead of raw session-key fragments; exact raw keys remain in the authenticated FloorState for session and event correlation. The service rejects any handshake whose effective role and scopes differ from exactly `operator` and `operator.read`.

The PAP task panel shows every enabled recurring occurrence expected within the next hour, then up to eight later occurrences per job, globally sorted by forecast dispatch time. Disabled jobs have a separate chronological preview and are never labeled as upcoming executions. A stored scheduler jitter seed lets the read-only projector calculate the same stable ±5-minute offset as `pap tick`; without one, it labels the nominal schedule minute instead. Actual starts still depend on the scheduler running and job readiness.

For a synthetic check of the production bundle under the same strict CSP as the server, build first, then run `node --import tsx tests/browser/csp-server.ts` and open `http://127.0.0.1:5190/` in a browser. This fixture serves synthetic OpenClaw state and real local PAP task metadata. It makes no Gateway connection; the office figures are labeled as test agents.

For a local capacity and frame-rate check, run `npm run dev -w @pap/office-web` and open `/capacity.html?count=100&seconds=30`. The development-only page shows all 100 synthetic roster rows, pages the scene 12 seats at a time, and measures Pixi ticker completions plus independent browser animation frames after a three-second warmup. `seconds` accepts 10–120 and defaults to 10. Compare `/capacity.html?scene=0`, `?scene=canvas`, and `?scene=empty` before attributing a low reading to the office scene. Record the browser, viewport, map and machine in ignored local evidence; this fixture does not by itself establish the target 30 FPS requirement.

Open the production office with `?measure=1` to display local Pixi frame and SSE latency diagnostics in the footer. The frame meter warms up for three seconds, then counts 30 seconds of completed Pixi ticker callbacks and their average work time; it resets its window while the page is hidden. The SSE meter reports rolling P95 from server patch creation to the browser's next animation-frame callback, split into server-to-browser arrival and browser arrival-to-frame. A separate meter starts at a newly admitted structured event receipt that changes a status label on the current scene page and stops at the first Pixi frame completed after that scene revision has synced. It counts accepted foreground patches and completed SSE frame samples; below 90% sample coverage after 20 patches, the page marks that SSE result unsuitable for acceptance. Keep that tab foregrounded and record the browser, viewport, renderer and machine. These diagnostics do not prove physical pixel presentation or polling discovery. The ordinary URL hides them. They record timings only, never session contents.

For the browser transport fallback, start that fixture with `PAP_CSP_SSE_FAIL_COUNT=3`. The first three SSE requests return 503; the page should show the synthetic roster through HTTP snapshots and then label its transport “快照轮询”. `GET /test/requests` reports the SSE attempt count. This exercises the local browser transport only.

Development-only `/visibility-host.html` drives the browser host through three synthetic SSE failures, then checks that hiding cancels a pending fast poll and returning immediately reads a snapshot, reconnects SSE and reports a visible viewer. `/pap-refresh.html` holds the first PAP task response until a newer response has rendered, then verifies that the older response cannot replace the task list. These fixtures are excluded from the production build.

For a real Gateway reconnect check without interrupting the main office service, set `PAP_PROBE_GATEWAY_PORT` to the local Gateway port and start `node --import tsx tests/browser/reconnect-proxy.ts`. In a second terminal, supply the same read-only Gateway observation credential through `OPENCLAW_GATEWAY_TOKEN`, choose one already selected agent through `PAP_PROBE_AGENT_ID`, and start `node --import tsx tests/browser/reconnect-observer.ts`. After its aggregate output reports one fresh live row, send `POST http://127.0.0.1:18791/drop` from localhost. The observer prints aggregate connection, freshness, running-status counts and epoch changes only. Confirm an offline stale row retaining its business status, followed by a new live, fresh baseline, then stop both probe processes. Recovery across a business-state change during the interruption requires a separate live observation.

To check that a failed reconciliation read does not make a healthy SSE stream appear offline, use `PAP_CSP_STATE_FAIL_AT=2 PAP_CSP_INVALID_PATCH_DELAY_MS=800` with the same fixture. It sends one invalid patch after the SSE baseline so the browser requests a fresh snapshot; that second HTTP read returns 503. The roster and “SSE” transport label should remain visible.

To check theme fallback under that CSP, build the temporary browser entry with `npm run build -w @pap/office-web -- --mode csp-theme`, run the same fixture server, then open `/theme-fallback.html`. The fixture requests a missing custom map before the owned map. Restart the fixture server with `PAP_CSP_HIDE_OWNED_MAP=1` to verify the resource-error and DOM-roster path when both maps fail. Run the normal `npm run build` afterward; it removes the test page from `dist`.

To check the graphics recovery UI, build the temporary entry with `npm run build -w @pap/office-web -- --mode csp-gpu`, run the same strict-CSP fixture server, and open `/gpu-recovery.html`. The test control dispatches a cancelable context-loss event to the current canvas. Send one event, wait for the scene to rebuild, and repeat until the fourth event exhausts the shared budget. The canvas should hide while the DOM roster and details remain usable. This tests browser wiring with synthetic events, not a real GPU failure. Run the normal `npm run build` afterward.

To observe selected sessions after explicit selection, place a local config at `../var/office-floor/config.json` following `config.example.json`, and supply `OPENCLAW_GATEWAY_TOKEN` only in the local service environment for the initial connection. `PAP_OFFICE_CONFIG` can select another local config path. Do not commit this config or token. No sessions are read, and no device identity is created, when the config is absent or `selectedAgentIds` is empty.

For selected IDs, startup reads `openclaw agents list --json` locally and keeps only those IDs' display identity names. Sessions from one selected agent share a stable appearance key but remain separate figures. Explicit names and appearance keys in the ignored office config take precedence. If the CLI identity list is unavailable, session labels remain the fallback. An empty selection does not read the identity list.

With selected agents configured, the service creates an Ed25519 device identity in ignored `../var/office-floor/device-identity.json` with private file permissions. The Gateway may require approval of this new device. If it issues a device token, the client saves it in ignored `../var/office-floor/device-token.json` only when its scopes are exactly `operator.read` and its Gateway, device and role match. A stored broader-scope token or damaged identity fails closed. Target pairing and token issuance require separate verification.

## Current capability boundary

The server projects only allowlisted session rows and whitelisted metadata. It attempts `sessions.subscribe`, then falls back to `sessions.list` polling when necessary; per-session message subscriptions are attempted independently for visible rows, even when the roster uses polling. A confirmed unsupported message-subscription method is not retried until reconnection. It reconciles overlapping pages by `snapshotAt`, links only unambiguous visible parent and child sessions, and clears the projected view if list or connection authorization is denied. All Gateway reads share a 10-per-second, four-concurrent quota. The selected session's existing card is read only through `progressCard.get` when the Gateway advertises the owner-scoping capability. The response's scoped session key must match the requested owner and key before the card is attached; unverified alias mappings fail closed. Keyed rows update held sessions promptly; per-run sequence gaps make a uniquely matched session stale until calibration. Pinned `chat` terminal events update only uniquely matched active runs and exclude message text; a terminal fence prevents older list reads from restoring an ended run. Paired `session.operation` compaction receipts affect only the held session instance and survive list calibration. A `session.tool` event, or a scoped tool-stream `agent` event from the pinned Gateway's hidden-run path, may update the current tool only when its run, agent, key and session instance match one fresh active row; arguments and results are discarded, and a tool result does not mark the run failed. Tool coverage remains unverified until a scoped start/update/result sequence is observed on the target Gateway. The pinned SDK coordinates message observer leases and releases them after session removal or replacement. Local host callbacks persist the SDK's device identity and issued token, but target pairing requires separate verification. The pinned 2026.9.4 subscription schema has no `subscriptionId` field, so the newer identified-observer contract remains unverified on that version. The installed Gateway guards question events and `question.list` with `operator.questions` and approval events with `operator.approvals`; an exact `operator.read` observer has neither scope. Its blocking-input capability is therefore labeled forbidden, and no question text or silence is used to infer waiting. Narration remains unverified. A disconnected Gateway leaves prior business status visible with stale freshness.

The visual scene consumes only `FloorState` and supports a 12 seat page plus a complete DOM list. It uses an original validated Tiled map, the pinned MD procedural drawing pipeline with eight new recipes, stable seats and camera. An optional theme that fails to load falls back to the owned office once. The scene uses a shared recovery budget and has a DOM list fallback. Synthetic 20-cycle mount and context-loss browser checks passed; physical GPU failure and portal acceptance remain open.

The scene follows the browser's `prefers-reduced-motion` setting. In reduced motion, characters sit at their seats, character and monitor frames stop changing, the camera snaps to the selected seat, and a completed round uses a static checkmark instead of the transient success ring. Changing the system setting updates the mounted scene without clearing its session state.
